1. **Architecture** — MVVM or MVI, three clear layers (UI/domain/data), dependency injection. No DB/API call directly inside a screen file.
2. **State management** — one source of truth per screen; survives config changes/process death.
3. **Git** — GitHub repo, feature branches, PRs reviewed by teammate, meaningful commits, both members commit every week. *(See "Git workflow" section below — Claude Code now handles this automatically on every task.)*
4. **UI states** — every data-loading screen handles loading/empty/error/success, errors offer retry.

6. **Stability** — no crash during demo; handles no internet, empty response, invalid input.
7. **Testing** — at least 3 unit tests (ViewModel/repository logic) + 1 UI test, all passing.
8. **README** — what the app does, how to run it, architecture diagram, 4-5 screenshots, known limitations.
9. **Build** — a signed APK or installable build the mentor can run (not just "runs on our emulator").
10. **Demo** — 15-min live demo + 10-min code Q&A. Both members must be able to explain ANY part of the code, not just their own.

Out of scope for all teams: no real payments, no real user data, no custom backend. Local mock data / local storage is explicitly an accepted approach (not just Firebase) — this project deliberately uses local SQLite, not Firebase, since notes are on-device content with no real sync need.

If there's already an in-progress feature branch with related uncommitted work, keep using it rather than branching again — and if that branch touches the same files as your new task, branch from it (not from `main`) so you don't diverge from unpushed work and set up a painful merge later.

Small follow-up fixes found while testing the same feature (a bug caught during manual testing, a tweak the user asks for right after) become additional commits on that same branch, not new branches.

## Architecture (established, follow this pattern for all new code)

Three-layer split:

- `lib/domain/` — `note.dart` (the `Note` model: id, title, **blocks** (see below), tags, isPinned, isLocked, colorValue, createdAt, updatedAt, **archivedAt** — all immutable/`final`, edited via `copyWith`), `note_block.dart` (the `NoteBlock` model — see "Note content model" below), `note_repository.dart` (abstract interface, expanded for archiving — see below), `tag.dart`/`tag_repository.dart`, `settings_repository.dart` (dark/light mode persistence contract) — no implementations, just contracts.
- `lib/data/` — `note_repository_impl.dart`, `tag_repository_impl.dart`, `settings_repository_impl.dart` (backed by `shared_preferences`) implement the domain interfaces. `app_database.dart` (`AppDatabase.instance`) is the single shared `sqflite` connection both note and tag repos use — **schema is now at `version: 5`**: v2 added the `tags` table, v3 added `notes.colorValue`, v4 added `notes.blocksJson`, v5 added `notes.archivedAt`. Each bump has an `onUpgrade` step so existing installs migrate in place; `Note.fromMap` also has a **legacy-data fallback** that reconstructs `blocks` from the old flat `body`/`photoPaths`/`voiceMemoPath` columns for any note saved before v4, so nothing already on a device gets lost.
- `lib/ui/` — screens, `lib/ui/view_models/` for ViewModels (`extends ChangeNotifier`, call `notifyListeners()` on state change), and `lib/ui/app_theme_colors.dart` — small `BuildContext`-based helper functions (`pillColor(context)`, `primaryTextColor(context)`, `secondaryTextColor(context, [opacity])`, `scaffoldBg(context)`, `isDarkContext(context)`) that every screen uses instead of hardcoding dark-theme colors, so the light/dark toggle (see below) actually works everywhere instead of just flipping `ThemeData.brightness` and leaving hardcoded `Colors.white`/`Color(0xFF1C1C1E)` broken in light mode.

**Note content model**: a note's content is `Note.blocks: List<NoteBlock>` (`lib/domain/note_block.dart`) — an ordered sequence of `text`/`photo`/`audio` blocks, not a single string. This is what lets images and voice memos sit *inline* in the note (type before and after an attachment, not just in a fixed row below all the text). `Note.body`/`photoPaths`/`voiceMemoPaths` still exist as **derived getters** computed from `blocks` (not stored fields) so search matching, gallery previews, and the "has images"/"has recordings" search filters didn't need to change. Each text block also carries its own `bold`/`italic` flags — see "Rich text scope decision" below.

**Dependency injection**: done via the `provider` package (also used for state management — no separate DI package). Each real repository impl is created once in `main.dart` via `MultiProvider`/`Provider<T>`, and every ViewModel receives it through its constructor (typed as the abstract interface, never the concrete impl) — this is what makes ViewModels testable with a fake repository later.

**UI states pattern**: ViewModels expose an `enum` status (e.g. `NotesListStatus { loading, empty, error, success }`), and screens `switch` on it to render distinct UI per state — this satisfies requirement #4 directly, don't build screens without this pattern.

**Note editing UX decision (revised)**: Note Detail screen is still always-editable (iOS Notes style, no Save/Discard buttons) but is **no longer a single TextField** — it's a scrollable `Column` of block widgets (one `TextField` per text block, an `Image.file` per photo block, a playback row per finished audio block). Tapping blank space below the last block focuses the end of the last text block (a `GestureDetector` + `ConstrainedBox(minHeight: viewport)` trick, since a plain `SingleChildScrollView` doesn't auto-fill remaining space the way the old single `expands: true` TextField did). **Pressing Enter inside a text block splits it into a new block** (`NoteDetailViewModel.splitTextBlockIntoParagraphs`) rather than inserting a `\n` within the same block — this is what makes bold/italic apply per-paragraph instead of to the whole note (see "Rich text scope decision" below), and focus is moved to the new block afterward via `WidgetsBinding.instance.addPostFrameCallback`. Auto-saves via a 500ms debounce per keystroke (`Timer` in `NoteDetailViewModel`); `saveNow()` forces an immediate save on navigation away (via `PopScope`) and after any structural change (photo/audio insert, tag add/remove, bold/italic toggle) so those aren't lost to the debounce window.

**Rich text scope decision — REVISITED, see "Rich-text rewrite attempt" below.** Mohamed originally asked for images/audio inline in the text *and* bold/italic styling. True word-level rich text (select a few words mid-sentence, bold just those) would need a real rich-text engine (e.g. `flutter_quill`) — a large, risky integration this close to the deadline (new document format, data migration, custom embed builders for photo/audio). **Explicitly decided against it at the time** and went with **block/paragraph-level** bold/italic instead — each block has its own `bold`/`italic` flag, toggled via a small B/I toolbar that appears above whichever block currently has focus. **This decision was later reopened**: after living with paragraph-level formatting, Mohamed asked for genuine selection-based bold/italic after all, was re-informed of the same tradeoff, and explicitly chose to proceed with `flutter_quill` anyway — see "Rich-text rewrite attempt (flutter_quill)" below for the full story, now resolved. The block-level approach described in this paragraph is what's still live on `main`; the `flutter_quill` replacement is committed on `feature/voice-memo-transcripts` and is the shipping direction going forward.

**Theme system**: `ThemeViewModel` (`lib/ui/view_models/theme_view_model.dart`) is a root-level `ChangeNotifierProvider` in `main.dart`, above `MaterialApp`, backed by `SettingsRepository`/`shared_preferences` (defaults to dark). `MaterialApp` is wrapped in a `Consumer<ThemeViewModel>` and defines **two complete `ThemeData`s** (`theme:` light, `darkTheme:` dark), switched via `themeMode: themeViewModel.themeMode`. This only works because every screen was retrofitted to read colors through `app_theme_colors.dart` instead of hardcoding a single dark palette — see the note in the `lib/ui/` bullet above. Toggled from Settings → Appearance → Dark Mode switch.

**Archive/soft-delete model**: `NoteRepository.deleteNote`/`deleteNotes` are now **permanent** deletion (file cleanup + DB row removal) — they're used internally for purging expired archives, not for the user's everyday "delete a note" action anymore. The everyday delete path is `archiveNote`/`archiveNotes` (sets `archivedAt`, note just stops appearing in `getNotes()` — `WHERE archivedAt IS NULL`), `restoreNote` (clears it), and `getArchivedNotes()`. `NotesListViewModel.archiveMaxAge` (`Duration(days: 3)`) is the retention window; `purgeExpiredArchivedNotes(maxAge)` is called opportunistically at the top of every `loadNotes()`/`ArchivedNotesViewModel.load()` (no background job/platform scheduling — this is a class project, not worth the complexity) so expired notes get swept the next time either screen loads. The existing 4-second swipe-to-delete Undo window still works exactly as before and is a separate, earlier layer: `deleteNoteWithUndo` optimistically removes the note from the visible list immediately and only calls `archiveNote` after a 4s `Timer` (canceled if the user taps Undo in that window) — so the full lifecycle is *swipe → 4s Undo window → archived for 3 days (recoverable via Settings → Archived Notes) → permanently purged*.

## Rich-text rewrite attempt (flutter_quill) — DONE, committed, keyboard bug resolved

**Why this exists**: after the text-editing fix above, Mohamed asked for genuine selection-based bold/italic ("select anything in the note and change what I want"), which is real per-word/per-selection rich text — the exact thing the original "Rich text scope decision" (still documented above in Architecture) had explicitly ruled out as too risky this close to the deadline. Claude Code re-explained the tradeoff (a plain `TextField` can only render one uniform style for its whole content; true mixed styling needs a real rich-text engine) and Mohamed explicitly chose to proceed with `flutter_quill` anyway, fully informed of the risk. **This is a deliberate, informed re-decision, not scope creep** — but it directly touches graded Req 1 (core note creation) on the actual deadline day.

**What was actually built** (verified against the real `flutter_quill` 11.5.1 source in the pub cache, not just its docs — several API details there are non-obvious or differ from what most tutorials show):
- `Note.quillJson: String` (a JSON-encoded Quill Delta) replaces `Note.blocks: List<NoteBlock>` as the single source of truth for a note's whole content — text, photos, and voice memos all live inline in one `Document`. `NoteBlock`/`blocksJson` are kept **only** for one-time, read-time migration of notes saved before this change (`Note.fromMap`'s legacy branch now converts old blocks into an equivalent Quill delta instead of reconstructing a `List<NoteBlock>`) — no write-back migration, matching this app's existing legacy-fallback idiom. Schema bumped to **v6** (`quillJson TEXT NOT NULL DEFAULT ''`); the old `blocksJson` column is left in place, unused, not dropped (SQLite `ALTER TABLE DROP COLUMN` isn't worth the risk this close to the deadline).
- Photos are Quill's built-in `'image'` embed type holding the file path directly. Voice memos are a **plain** `Embeddable('audio', <json>)` carrying `{id, path, transcript}` — deliberately **not** using Quill's `CustomBlockEmbed`/`BlockEmbed.custom()` wrapper, which double-JSON-encodes the payload for no benefit here (`'audio'` doesn't collide with any built-in embed type), and would otherwise force importing `flutter_quill` into the domain layer just to decode it back out in `Note.voiceMemoPaths`/`hasChecklist`.
- `NoteDetailViewModel` now owns a `QuillController` instead of per-block `TextEditingController`/`FocusNode` maps; `NoteDetailScreen` renders one `QuillEditor` instead of a `Column` of block widgets, with custom `EmbedBuilder`s for `'image'`/`'audio'` (the audio one still renders the existing play/pause row, transcribe button, and 4-state transcript area from the section above, wrapped in a `Consumer<NoteDetailViewModel>` since transcription state doesn't flow through the Quill document itself).

### Keyboard bug — RESOLVED: it was an Android Studio emulator quirk, not app code

After this rewrite, tapping the Title field **or** the note body initially didn't bring up the on-screen keyboard on the Android Studio Pixel_8 emulator, even though Title is a plain, completely unmodified `TextField` untouched by this rewrite.

**Three fix attempts were made along the way, in order** — each was independently a real, necessary fix, but none of them was the actual cause:

1. `QuillEditorConfig(expands: true, scrollable: true)` — an invalid combination per the package's own layout assertion (see above). Fixed by removing `expands`/`scrollable` entirely (defaults match the working example).
2. Missing `flutter_localizations` + `FlutterQuillLocalizations.delegate` on the root `MaterialApp` — flutter_quill genuinely requires this (confirmed via its example app), and the app had zero explicit `localizationsDelegates` before this. Added `flutter_localizations` (Flutter SDK package) and the full delegate list (`GlobalMaterialLocalizations`, `GlobalCupertinoLocalizations`, `GlobalWidgetsLocalizations`, `FlutterQuillLocalizations`).
3. The Pixel_8 AVD's `config.ini` had `hw.keyboard=yes` (fixed to `no` + a full cold boot — see "Known environment gotchas").

**Root cause, found by switching to a real device**: with none of the above pinning it down, testing moved to Mohamed's real Samsung SM-A047F over wireless ADB (`adb tcpip 5555` + `adb connect <phone-ip>:5555`, since the USB cable was too short) — and the keyboard worked correctly there from the start. A screenshot on the emulator then showed the actual visual symptom directly: Gboard was stuck in its collapsed "floating toolbar" mode (a small vertical pill — backspace/enter/emoji/menu icons, no QWERTY keys) sitting where the real keyboard should be, which is exactly the known per-session Gboard quirk already documented in "Known environment gotchas" below. So this was never a `flutter_quill`/app bug — it was specific to that Android Studio emulator session. **Takeaway for next time**: if a keyboard-not-appearing report comes in again, check a real device (or a fresh emulator boot) before assuming it's a code regression.

## Known environment gotchas (don't re-debug these)

- `record: ^5.1.2` fails to build (`record_linux` missing interface methods) — must use `^7.1.1`.
- `flutter doctor`'s Android license check can show a false "unknown" status on newer Android SDK cmdline-tools even after real licenses are accepted via Android Studio's GUI — this is cosmetic; the real test is whether `flutter run` actually builds, not what `flutter doctor` reports.
- Windows PATH for Flutter sometimes doesn't propagate to already-open terminal windows — always fully close and reopen the terminal after any PATH change.
- `.claude/settings.local.json` in this repo is actively managed by Claude Code's own tool-approval flow (it appends an exact-match rule every time a new command is approved). Hand-editing it to add `permissions.defaultMode: "bypassPermissions"` gets silently overwritten the next time a new command needs approval — don't rely on that file for a persistent "stop asking" fix; it has to be set elsewhere (e.g. `~/.claude/settings.json`) or just accepted as a per-command allowlist that grows over time.
- Mohamed prefers to drive manual on-device testing himself (tapping through the emulator) once a feature is implemented, rather than having Claude Code automate it via `adb shell input tap`/screenshots — give him a numbered list of what to check instead of continuing to script the interaction. **Concrete evidence this session**: blind coordinate-based `adb shell input tap` repeatedly missed intended targets once the keyboard was open or a layout shifted (e.g. tapping "Record Audio" landed on "Take Photo" or "Choose Photo" instead, multiple times, even after recalculating coordinates from a fresh screenshot) — this isn't just a preference, it's genuinely unreliable for anything beyond a single simple tap on a static screen. Mohamed explicitly asked Claude Code to stop doing this mid-session ("youre wasting tokens ill do it man its faster if i do it"). Default to a single before/after screenshot or a quick `flutter analyze`/build check for verification; hand off multi-step interaction testing to Mohamed with a numbered checklist.
- **Flutter's `SnackBar` pauses its own auto-dismiss timer while its hosting route isn't the topmost route** (e.g. while the user has navigated into another screen) — it can look "stuck" for minutes even though it did nothing wrong, since it resumes counting down once you return. Don't use `SnackBar` for anything where an accurate, always-correct dismiss time actually matters (e.g. tied to a real background timer, like the undo-then-archive flow) — the notes list's undo banner was rebuilt as a custom state-driven overlay for exactly this reason; see the "Undo banner bug + fix" bullet above. Do reach for this pattern (state field on a ViewModel + a plain overlay `Container` instead of `ScaffoldMessenger.showSnackBar`) again for anything similar rather than reaching for `SnackBar` by default.
- **To inspect the app's SQLite DB directly from this machine** (much faster/more reliable than verifying persistence bugs through the UI): `adb -s <device> exec-out run-as com.example.snapnote cat databases/snapnote.db > local.db` (must be `exec-out`, not `adb shell ... cat > file` — the latter does newline translation on Windows and silently corrupts the binary file, "database disk image is malformed"), then inspect with a local `sqlite3` — one's already available on this machine at `C:\Users\pv\AppData\Local\Android\Sdk\platform-tools\sqlite3` (the emulator's own shell doesn't have `sqlite3`, `run-as ... which sqlite3` fails). Used this to directly confirm the undo-banner bug (above) was a UI-only issue, not an actual data bug, by checking `archivedAt` timestamps.
- **Pixel_8 AVD (`C:\Users\pv\.android\avd\Pixel_8.avd\config.ini`) is set to `hw.keyboard=no`** (this machine's own AVD, already fixed — don't "fix" it again as if it were still `yes`). `hw.keyboard=yes` tells Android a physical keyboard is attached, which suppresses the on-screen keyboard for the entire OS, not just this app; confirm via `adb shell dumpsys input`'s `BuiltInKeyboardId` (a real device id like `14` = a hardware keyboard registered, `-2` = none, i.e. correctly software-keyboard-only). Changing this flag requires a **full cold boot** to take effect, not a normal restart. **Important caveat, learned the hard way**: this fix alone did NOT resolve a separate "keyboard doesn't appear" report during the flutter_quill rewrite — that one turned out to be the Gboard floating-toolbar quirk below, confirmed by testing on a real device instead. Don't assume this AVD setting is the answer any time a keyboard-not-appearing report comes in; verify against the actual current symptom (ideally on real hardware) first.
- Gboard on a freshly-created/wiped AVD can default to a collapsed "floating toolbar" mode (a small vertical pill with just backspace/enter/emoji/menu icons, no visible QWERTY keys) instead of the full keyboard on first use — distinct from the `hw.keyboard` issue above, fixable per-session via Gboard's own "Show on-screen keyboard" menu item (accessible from the pill). This is what turned out to be causing the flutter_quill "keyboard doesn't appear" report — see "Rich-text rewrite attempt (flutter_quill)" above.
- **Wireless ADB, when the USB cable is too short/inconvenient**: with the device already connected over USB, `adb tcpip 5555` switches its adbd to listen over the network (this restarts adbd, which drops the current USB debug session — including mid-`flutter run`, so expect to relaunch), then `adb connect <device-wifi-ip>:5555` (get the IP via `adb shell ip -f inet addr show wlan0`) attaches over Wi-Fi; the cable can come out after that. The wireless connection can drop on its own (e.g. if the phone's screen locks) — `adb devices` shows it missing, and a plain `adb connect <ip>:5555` again reconnects it without needing to redo `tcpip` or touch the cable.
- **A release-signed build and a debug build can't coexist/upgrade over each other** — `adb install -r` fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE: ... signatures do not match` any time you switch between `flutter run` (debug key) and a `flutter build apk --release` install (the real release keystore), in either direction. Fix is always the same: `adb uninstall com.example.snapnote` first (this wipes the app's local data — notes, settings — so warn before doing it), then install the other one fresh.
- **`adb shell run-as <package>` only works against a debuggable build** — fails with `run-as: package not debuggable` against an installed release build. So the "inspect the SQLite DB / cache directory directly" technique above only works while a **debug** build is installed; if a release build is currently installed and you need to poke around its files, either reason from the code instead, or temporarily swap in a debug build (mind the data wipe from the signature-mismatch point above).
- **Android's release-build resource shrinker strips any drawable only referenced by a string constant** (not a direct Dart/Kotlin symbol) — e.g. a notification icon name passed through a plugin's platform channel, like `AndroidInitializationSettings('ic_stat_live')`. Debug builds don't shrink resources at all, so this class of bug is invisible until you actually test a signed release build specifically — see the "Go Live silently failing in release builds" bullet above for the concrete instance and fix (`tools:keep` in `android/app/src/main/res/raw/keep.xml`). General takeaway: **always smoke-test the actual release APK**, not just debug, before considering a feature done — this bug would never have been caught otherwise.
