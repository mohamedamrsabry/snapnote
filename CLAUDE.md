## Grading context — 10 shared requirements checked across ALL teams (not just this one)

1. **Architecture** — MVVM or MVI, three clear layers (UI/domain/data), dependency injection. No DB/API call directly inside a screen file.
2. **State management** — one source of truth per screen; survives config changes/process death.
3. **Git** — GitHub repo, feature branches, PRs reviewed by teammate, meaningful commits, both members commit every week. *(See "Git workflow" section below — Claude Code now handles this automatically on every task.)*
4. **UI states** — every data-loading screen handles loading/empty/error/success, errors offer retry.
5. **Permissions** — runtime permissions need a rationale screen + a working "permanently denied → Settings" path.
6. **Stability** — no crash during demo; handles no internet, empty response, invalid input.
7. **Testing** — at least 3 unit tests (ViewModel/repository logic) + 1 UI test, all passing.
8. **README** — what the app does, how to run it, architecture diagram, 4-5 screenshots, known limitations.
9. **Build** — a signed APK or installable build the mentor can run (not just "runs on our emulator").
10. **Demo** — 15-min live demo + 10-min code Q&A. Both members must be able to explain ANY part of the code, not just their own.

Out of scope for all teams: no real payments, no real user data, no custom backend. Local mock data / local storage is explicitly an accepted approach (not just Firebase) — this project deliberately uses local SQLite, not Firebase, since notes are on-device content with no real sync need.

## Git workflow — Claude Code drives this automatically, no need to ask each time

Neither team member is comfortable with git, so **Claude Code owns the routine git operations as a normal part of finishing any task** — this is a standing authorization, not something to confirm before doing each time. This applies the same way on both Mohamed's and Tya's machines/sessions.

- **Never commit or push straight to `main`.** At the start of a task: `git checkout main`, `git pull`, then `git checkout -b feature/short-description` (or `fix/...`). If there's already an in-progress feature branch with related uncommitted work, keep using it rather than branching again.
- **Commit in logical, meaningful chunks**, not one giant commit — group by distinct piece of functionality, ordered so each commit still builds on its own (e.g. a repository-layer change a UI feature depends on should be committed before that UI feature). Small follow-up fixes found while testing the same feature (a bug caught during manual testing, a tweak the user asks for right after) become additional commits on that same branch, not new branches.
- **Push and open a PR** once a task's work is committed: `git push -u origin <branch>` (first push) or `git push` after. This machine doesn't have the `gh` CLI installed, so `git push` itself prints a direct PR-creation link (`https://github.com/mohamedamrsabry/snapnote/pull/new/<branch>`) — hand that link to the user. Check `gh --version` first in case a future session (e.g. Tya's machine) does have it installed, and use `gh pr create` instead if so.
- **Never auto-merge a PR.** Merging is left to Mohamed or Tya clicking the button on GitHub themselves — that's what actually satisfies the graded "PRs reviewed by teammate" requirement (Shared Requirement #3, part of the 5-point "Teamwork & Git" criterion, specifically checked at Checkpoint 1) and keeps a real human decision before anything lands on `main`.
- After a PR is merged, the next task starts fresh: `git checkout main`, `git pull`, then branch again.
- **Destructive git operations are NOT covered by this standing authorization** — force-push, `reset --hard`, rewriting history, deleting branches still need explicit confirmation from the user first, per normal safety practice.

## Architecture (established, follow this pattern for all new code)

Three-layer split:

- `lib/domain/` — `note.dart` (the `Note` model: id, title, body, photoPaths, voiceMemoPath, tags, isPinned, isLocked, createdAt, updatedAt — all immutable/`final`, edited via `copyWith`) and `note_repository.dart` (abstract interface: getNotes, getNoteById, addNote, updateNote, deleteNote — no implementation, just contracts).
- `lib/data/` — `note_repository_impl.dart` implements the interface using `sqflite` (local SQLite). Singleton DB connection pattern. `toMap()`/`fromMap()` on `Note` handle the conversion (lists joined as comma-separated strings, no native list type in SQLite).
- `lib/ui/` — screens, and `lib/ui/view_models/` for ViewModels (`extends ChangeNotifier`, call `notifyListeners()` on state change).

**Dependency injection**: done via the `provider` package (also used for state management — no separate DI package). One real `NoteRepositoryImpl` is created once in `main.dart` via `Provider<NoteRepository>`, and every ViewModel receives it through its constructor (typed as the abstract `NoteRepository`, never the concrete impl) — this is what makes ViewModels testable with a fake repository later.

**UI states pattern**: ViewModels expose an `enum` status (e.g. `NotesListStatus { loading, empty, error, success }`), and screens `switch` on it to render distinct UI per state — this satisfies requirement #4 directly, don't build screens without this pattern.

**Note editing UX decision**: Note Detail screen is a single always-editable screen (iOS Notes style) — tap anywhere to edit, no separate edit mode, no Save/Discard buttons. Auto-saves via a 500ms debounce (`Timer` in `NoteDetailViewModel`, cancelled/restarted on every keystroke) so it doesn't hit the DB on every character. `saveNow()` forces an immediate save on navigation away (via `PopScope`) so the last debounce window isn't lost.

## What's built and confirmed working

- Full data layer: `Note` model, repository interface + SQLite implementation. `NoteRepositoryImpl.deleteNote`/`deleteNotes` also delete the note's photo/voice-memo files from `getApplicationDocumentsDirectory()` before removing the DB row(s) (`_deleteAttachmentFiles`) — this satisfies the project's explicit Definition of Done ("delete the note — its files are removed from storage") and part of the graded Technical Challenge. Fetches the note(s) by id first (via `getNoteById`/a `WHERE id IN (...)` query) to know which files to remove, since the row is gone after the delete. Still open: no image downsizing/caching — the other half of the Technical Challenge ("keeping large images from blowing up memory") is unaddressed.
- `NotesListViewModel` + `NotesListScreen` — loading/empty/error/success states all implemented, error state has working retry.
- `NoteDetailViewModel` + `NoteDetailScreen` — create/edit note, debounced auto-save, tested end-to-end (create → persist → close → reopen → data intact).
- Navigation wired both directions (list ↔ detail) with auto-refresh on return.
- `permission_request_screen.dart` — ONE reusable screen (not two) handling both the rationale view and the permanently-denied view for any permission (camera or mic), switching internally based on `PermissionStatus`. Includes `ensurePermission(context, permission, featureName)` helper function for other code to call. **Wired into both the camera trigger (Take Photo) and the mic trigger (Record Audio).**
- Photo attachment — fully implemented and tested end-to-end on an Android emulator. Paperclip icon in `NoteDetailScreen`'s AppBar opens a bottom sheet (Take Photo / Choose Photo / Record Audio, matching the Figma wireframe). Take Photo goes through `ensurePermission` (camera) then `image_picker`'s camera source; Choose Photo uses `image_picker`'s gallery source (no runtime permission needed — modern Android's system photo picker handles it). `addPhoto(File)` in `NoteDetailViewModel` copies the picked file into `getApplicationDocumentsDirectory()` under a UUID-based name (picker's temp file can be cleared by the OS), appends the new path to `Note.photoPaths`, and saves immediately (`saveNow()`, not the debounce). A small thumbnail row under the note body shows attached photos (placement is temporary — see the Figma-driven UI pass in "What's NOT built yet"). Required adding `<uses-permission android:name="android.permission.CAMERA"/>` to `AndroidManifest.xml`, which was missing. Also fixed a bug in `NoteDetailViewModel._save()` where its "don't save a fully empty note" guard checked only title/body, so a new note with just a photo and no typed text would silently fail to save — guard now also checks `photoPaths`.
- Voice memo record/play/delete with duration display — fully implemented and tested end-to-end on an Android emulator (this is graded Requirement #3 verbatim). "Record Audio" in the paperclip menu goes through `ensurePermission` (microphone) then starts recording immediately via `record`'s `AudioRecorder` (`RecordConfig()` default encoder is AAC, producing `.m4a`), saved into `getApplicationDocumentsDirectory()` with a UUID filename — same pattern as photos. `NoteDetailViewModel` exposes `isRecording`/`isPlaying`/`recordingDuration`/`voiceMemoDuration`/`playbackPosition` plus `startRecording()`/`stopRecording()`/`playVoiceMemo()`/`pausePlayback()`/`deleteVoiceMemo()`; playback uses `audioplayers`' `AudioPlayer`, listening to `onPlayerStateChanged`/`onDurationChanged`/`onPositionChanged` to keep those in sync. Stopping a recording saves immediately (`saveNow()`, not the debounce). Navigating back mid-recording auto-stops it first (`_handleBack` checks `isRecording`) so the mic doesn't stay active and the recording isn't silently lost. A row under the note body shows "Recording... 0:07" (live-updating) with a stop button while recording, or a play/pause control + "0:00 / 0:12" position/total display + a delete (🗑) button once a voice memo exists (same temporary placement caveat as photos). `deleteVoiceMemo()` stops playback if active, deletes the audio file from disk, and clears `voiceMemoPath`. Required adding `<uses-permission android:name="android.permission.RECORD_AUDIO"/>` to `AndroidManifest.xml`. `_save()`'s empty-note guard extended again to also check `voiceMemoPath`. Two things worth knowing: (1) `Note.copyWith` originally used the plain `value ?? this.value` pattern for `voiceMemoPath`, which can never explicitly null a field back out — added a `clearVoiceMemo` bool param to `copyWith` specifically to support deletion; (2) since duration isn't itself persisted (only the audio file is), reopening a note with an existing voice memo preloads its length via `audioplayers`' `setSourceDeviceFile()` + `getDuration()` in the ViewModel constructor (no playback triggered) — without this, the duration read as 0:00 until the user pressed play once. Also fixed a stability bug found in testing: the playback listener (`AudioPlayer.onPlayerStateChanged`) could fire `notifyListeners()` after the `NoteDetailViewModel` was already disposed (e.g. navigating away while a clip was still playing), throwing "used after being disposed" — fixed by storing the `StreamSubscription` and cancelling it in `dispose()` before disposing the player. **Known emulator quirk**: recording captures real audio (duration/metadata read back correctly) but playback may produce no audible sound on some Android emulator configs — no exceptions in the log, so this looks like an emulator audio-output routing issue (check the AVD's Advanced Settings → Audio output is enabled, and host volume), not an app bug; unconfirmed on a real device yet.
- Search + gallery view + multi-select delete on the notes list — fully implemented and tested end-to-end on an Android emulator. Search icon in `NotesListScreen`'s AppBar opens `SearchScreen` (its own `SearchViewModel`, scoped locally the same way `NoteDetailViewModel` is — not added to `main.dart`'s root providers): a search bar filters notes by title/body (case-insensitive substring match), plus 4 toggleable filters — Locked Notes / Notes with Checklists / Notes with Images / Notes with Recordings — AND-combined with each other and the text query, shown as a browsing list before anything is typed or selected. **Locked Notes and Notes with Checklists always return zero results for now** — `isLocked` is persisted-but-dead data (no lock/unlock UI exists anywhere), and there's no checklist feature at all (no field, no model) — both are separate future features; this is expected, not a bug. The home screen's 3-dot menu (`PopupMenuButton`) adds "View as Gallery" (toggles a 2-column `GridView`: a note's first photo as the thumbnail if it has one, otherwise a small preview of the note's body text) and "Select Notes" (multi-select mode — tapping a note toggles a checkmark instead of opening it; the AppBar shows a live count and a button that reads "Delete All" when nothing is selected yet or "Delete" — selected notes only — once something is; deletes fire immediately with no confirmation dialog, per the user's own call). Added `NoteRepository.deleteNotes(List<String> ids)` (SQL `WHERE id IN (...)`) for the bulk-delete case, alongside the pre-existing single-id `deleteNote`. New files: `lib/ui/search_screen.dart`, `lib/ui/view_models/search_view_model.dart`. Two bugs found and fixed during manual testing: (1) the search bar's clear (✕) button reset the ViewModel's `query` but not the `TextField`'s own displayed text, since the field had no `TextEditingController` — fixed by adding one and clearing it explicitly alongside `viewModel.clear()`; (2) the gallery card's fallback for a photo-less note was a generic icon — changed to a small body-text preview instead, per the user's request.

## Known environment gotchas (don't re-debug these)

- `record: ^5.1.2` fails to build (`record_linux` missing interface methods) — must use `^7.1.1`.
- `flutter doctor`'s Android license check can show a false "unknown" status on newer Android SDK cmdline-tools even after real licenses are accepted via Android Studio's GUI — this is cosmetic; the real test is whether `flutter run` actually builds, not what `flutter doctor` reports.
- Windows PATH for Flutter sometimes doesn't propagate to already-open terminal windows — always fully close and reopen the terminal after any PATH change.
- `.claude/settings.local.json` in this repo is actively managed by Claude Code's own tool-approval flow (it appends an exact-match rule every time a new command is approved). Hand-editing it to add `permissions.defaultMode: "bypassPermissions"` gets silently overwritten the next time a new command needs approval — don't rely on that file for a persistent "stop asking" fix; it has to be set elsewhere (e.g. `~/.claude/settings.json`) or just accepted as a per-command allowlist that grows over time.
- Mohamed prefers to drive manual on-device testing himself (tapping through the emulator) once a feature is implemented, rather than having Claude Code automate it via `adb shell input tap`/screenshots — give him a numbered list of what to check instead of continuing to script the interaction.
